## ADDED Requirements

### Requirement: 文章语言专业性

技术文章SHALL使用专业、准确的技术用语，避免以下口语化表述：
- 方言俚语（"都知道"、"就死定了"、"搞得定"等）
- 过度随意的口语（"然后呢"、"就是说要"等）
- 模糊表述（"大概"、"可能"、"好像"等，除非描述不确定性）
- 主观情绪化表述（"太棒了"、"太糟糕了"等）

文章SHALL优先使用：
- 标准技术术语（"实例化"而非"弄个对象"，"持久化"而非"存下来"）
- 精确的数据和事实（具体版本号、参数值、性能指标）
- 客观中立的描述语气
- 适当的类比和举例说明复杂概念

#### Scenario: 专业术语使用
- **WHEN** 描述技术概念或操作
- **THEN** 使用标准技术术语
- **AND** 示例：使用"实例化对象"而非"弄个对象"
- **AND** 示例：使用"执行持久化"而非"把数据存下来"

#### Scenario: 口语化表述检测
- **WHEN** 文章中出现"都知道"、"就死定了"、"搞得定"等口语化表述
- **THEN** 检查脚本标记为语言问题
- **AND** 建议替换为专业表述
- **AND** 示例："就死定了" → "会导致严重问题"

#### Scenario: 模糊表述改进
- **WHEN** 文章使用"大概"、"可能"、"好像"等模糊词汇
- **THEN** 检查是否描述不确定性
- **AND** 如描述确定事实，替换为精确表述
- **AND** 如描述不确定性，说明原因（如"由于版本差异，配置参数可能不同"）

### Requirement: 段落可读性

文章段落SHALL遵守以下可读性规则：
- 每段不超过5行文本（约100-150字）
- 每段表达一个核心观点
- 段落间使用过渡句衔接
- 长段落拆分为多个小段落或使用列表

长文章（超过3000字）SHALL在开头添加章节导航，使用列表形式列出主要章节标题。

#### Scenario: 段落长度控制
- **WHEN** 段落超过5行文本
- **THEN** 检查是否可以拆分为多个段落
- **AND** 或改用列表形式呈现要点
- **AND** 确保每个段落聚焦一个核心观点

#### Scenario: 章节导航添加
- **WHEN** 文章长度超过3000字
- **THEN** 在文章开头添加章节导航
- **AND** 导航格式：使用列表列出二级标题
- **AND** 示例：
  ```
  ## 文章目录
  - [Redis持久化概述](#redis持久化概述)
  - [RDB持久化机制](#rdb持久化机制)
  - [AOF持久化机制](#aof持久化机制)
  ```

### Requirement: 重点内容突出

文章SHALL使用以下方式突出重点内容：
- **加粗**：用于强调关键词、重要结论
- **引用块**：用于重要提示、警告、最佳实践
- **代码块**：用于命令、配置、代码示例
- **列表**：用于并列要点、步骤说明

对于关键结论和最佳实践，SHALL在相关章节末尾使用引用块总结。

#### Scenario: 重要结论突出
- **WHEN** 文章包含关键结论或最佳实践
- **THEN** 使用引用块（>）突出显示
- **AND** 示例：`> **最佳实践**：生产环境建议同时开启RDB和AOF两种持久化机制。`

#### Scenario: 关键术语强调
- **WHEN** 文章首次引入关键术语或概念
- **THEN** 使用加粗标记术语
- **AND** 后续出现时不再加粗
- **AND** 示例：**RDB持久化**是Redis的快照持久化机制

### Requirement: 内容组织逻辑

文章内容SHALL按照清晰的逻辑顺序组织：
- **教程类**：是什么 → 为什么 → 怎么做 → 注意事项
- **原理类**：背景 → 核心概念 → 工作原理 → 应用场景
- **实践类**：场景描述 → 问题分析 → 解决方案 → 效果验证
- **对比类**：概念A介绍 → 概念B介绍 → 对比分析 → 选择建议

每个章节SHALL有明确的主题，章节间通过过渡句或小结衔接。

#### Scenario: 教程类文章逻辑
- **WHEN** 编写技术教程文章
- **THEN** 先介绍"是什么"（基本概念和作用）
- **AND** 说明"为什么"（使用场景和优势）
- **AND** 详细讲解"怎么做"（步骤和实践）
- **AND** 最后列出"注意事项"（常见问题和最佳实践）

#### Scenario: 原理类文章逻辑
- **WHEN** 编写技术原理文章
- **THEN** 先介绍背景和动机
- **AND** 定义核心概念和术语
- **AND** 阐述工作原理和机制
- **AND** 最后说明应用场景和限制

### Requirement: 摘要撰写规范

文章摘要SHALL满足以下要求：
- 字数：200-300字
- 内容：概述文章主题、核心内容、目标读者
- 结构：问题背景 → 解决方案 → 关键要点
- 关键词：包含主要技术关键词，便于SEO

摘要应让读者快速判断文章是否与其需求相关。

#### Scenario: 标准摘要结构
- **WHEN** 编写文章摘要
- **THEN** 第一句概述文章主题和技术领域
- **AND** 中间部分说明文章解决的问题和方案
- **AND** 最后点出关键要点或收获
- **AND** 示例："本文介绍Redis的两种持久化机制RDB和AOF，分析各自的优缺点和适用场景，并给出生产环境的最佳实践建议。"

#### Scenario: 摘要关键词布局
- **WHEN** 撰写摘要
- **THEN** 包含文章的主要技术关键词
- **AND** 关键词自然融入语句，不堆砌
- **AND** 示例：摘要中包含"Redis"、"持久化"、"RDB"、"AOF"等关键词

### Requirement: 总结部分规范

长文章（超过2000字）SHALL在文末包含总结部分，总结SHALL满足以下要求：
- 概括文章核心要点（3-5条）
- 给出最佳实践建议
- 指出适用场景和限制
- 可选：提供进一步阅读链接

总结应让读者快速回顾文章精华，并指导实践。

#### Scenario: 标准总结格式
- **WHEN** 编写文章总结部分
- **THEN** 使用列表形式列出核心要点
- **AND** 每条要点简洁明了，不超过2行
- **AND** 最后给出最佳实践建议或注意事项
- **AND** 示例：
  ```
  ## 总结

  - RDB适合做冷备份，恢复速度快，但会丢失最近几分钟的数据
  - AOF数据安全性高，最多丢失1秒数据，但文件较大
  - 生产环境建议同时开启两种持久化机制
  - 根据业务需求选择合适的持久化策略
  ```

### Requirement: 参考资料规范

文章如引用外部资料，SHALL在文末列出参考资料：
- 格式：`- [标题](URL) - 简要说明（可选）`
- 优先列出官方文档和权威资料
- 资料链接应有效、可访问
- 避免列出过多无关链接

#### Scenario: 参考资料格式
- **WHEN** 文章引用了外部资料
- **THEN** 在文末"参考资料"章节列出链接
- **AND** 使用列表格式
- **AND** 示例：
  ```
  ## 参考资料

  - [Redis官方文档 - 持久化](https://redis.io/topics/persistence) - Redis持久化机制官方说明
  - [Redis设计与实现](http://redisbook.com/) - Redis内部实现原理
  ```

#### Scenario: 无参考资料处理
- **WHEN** 文章未引用外部资料
- **THEN** 不添加"参考资料"章节
- **AND** 文章内容基于作者经验和知识
